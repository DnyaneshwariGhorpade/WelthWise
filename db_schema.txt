1. System Overview & Core Technical Stack
WealthWise is a single-user-facing personal finance platform that consolidates income, expenses, assets, liabilities, and investments, then layers three AI-assisted analytical engines on top: Wealth Scoring, Stress Testing, and a Goal Conflict & Decision Advisor. The stack favors a lean, modular monolith over a distributed microservices footprint, matching the project's actual scale while keeping each engine cleanly separable for future extraction (OR-05).

Relational storage for accounts, financial records, goals, scores, and audit trails with enforced foreign-key integrity.
AI Advisory Layer
OpenAI API or Gemini API (pluggable)
Generates plain-language score explanations, resilience recommendations, and decision verdicts over HTTPS; swappable via configuration with no code change (OR-04).
Caching Layer
Redis (session & score cache)
Caches the latest computed Wealth Score and blacklists revoked JWTs so logout takes effect immediately (NFR11).
Background Job Runner
node-cron / Bull queue
Re-runs stress tests and goal-conflict checks automatically whenever underlying financial data changes materially (BR-03, BR-05).
Security & Identity
JWT (HS256), bcrypt, HTTPS / TLS 1.3
Stateless session authentication, salted password hashing, and enforced encrypted transport (NFR07–NFR09).
DevOps & Hosting

Containerized deployment supporting horizontal scaling as user load grows (NFR15).

3. Database Rules, Constraints & Policies
📌 Rule 1: Automatic Recalculation on Material Data Change (BR-03 & BR-05)
Whenever a user creates, edits, or deletes an income, expense, asset, or liability row, the API marks related stress_test_results.is_stale = TRUE and re-queues goal-conflict detection via the background job runner, so resilience and conflict data never drifts from the user's current numbers.
📌 Rule 2: Explainable-AI Data Binding (BR-04 & NFR-16)
Every row written to ai_insights, stress_test_results, or decision_evaluations must carry a non-null snapshot of (or direct reference to) the source figures that produced it. The application layer rejects any AI-generated output that cannot be paired with its supporting data before it reaches the UI.

4. Architect's Design Notes
4.1 Financial Input Validation & Data Integrity (NFR-04)
• Server-side validation rejects non-numeric, negative, or malformed amounts before they reach any analytical engine.
• All monetary columns use DECIMAL(14,2) rather than FLOAT, preventing floating-point rounding drift in net-worth and score math.
4.2 Stateless JWT Security & Session Expiry (NFR-07, NFR-11)
• JWTs carry a short expiry claim; a Redis-backed blacklist immediately invalidates a token on logout, even before natural expiry.
• Inactive sessions are force-expired after 15 minutes, enforced server-side on the next incoming request rather than trusted to the client alone.
4.3 Swappable AI Provider Abstraction (OR-04)
• All AI calls pass through a single internal ai-provider adapter interface rather than calling OpenAI or Gemini SDKs directly.
• Switching providers is a configuration-file change, isolating the rest of the system from vendor-specific request and response formats.
4.4 Explainability by Design (BR-04, NFR-16)
• Every score, alert, and recommendation is stored alongside the data snapshot that produced it, so the UI can always render “here's the data behind this” next to any AI-generated text.
• This applies uniformly to wealth_scores, stress_test_results, goal_conflicts, and decision_evaluations.
4.5 Modular Engine Boundaries for Future Reuse (NFR-14, OR-05)
• The Wealth Scoring, Stress Testing, and Goal Conflict engines are implemented as isolated backend modules with their own route, service, and table boundaries.
• Any one engine can later be extracted into an independent service without touching the others (OR-05).
